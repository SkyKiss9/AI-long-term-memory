## Long-running project continuity

- On the first project-related message and on a natural request to continue, use `$maintain-project-continuity`.
- New projects should get their own continuity records directly in that project. Old projects should be reactivated from a fresh conversation in that project's own workspace, then decide entry point, preserved records, and rollout scope from local evidence; do not batch-migrate or auto-unify old project entries from elsewhere.
- For an ordinary start, check the repository and manifest, then read only the current handoff. Do not load the complete overview, timeline, source index, or acceptance history, and do not give the user a recovery report unless asked.
- If the handoff is not enough, read only the timeline entry it points to and then the corresponding original source. Read complete history only for first-time reconstruction, an explicit audit, or a conflict that targeted lookup cannot resolve.
- Use the project's own original conversations, files, commits, pages, logs, or runtime results as evidence. Do not substitute global memory, unrelated old tasks, or internet material. Manifest states are descriptive only and never turn an ordinary start into an exam.
- The user speaks and decides normally; the AI owns source lookup, record maintenance, and write-back. Do not ask the user to administer the memory system or reconfirm an already clear decision.
- After material progress or a genuine closure, append one short timeline note: date, what changed, and the direct source; include the reason only when it matters. Refresh the handoff as a brief current bookmark instead of accumulating history. If nothing material changed, do not rewrite records.
- Continuity work stays in the background and must not override global user-facing communication rules. Give the user a plain-language conclusion and only the necessary explanation; do not expose code blocks, commands, paths, logs, configuration text, or internal investigation details unless requested.
- Continuity record maintenance does not authorize changes to business code, business data, configuration, formal workbooks, online content, or another project. Follow the applicable authorization boundary for those changes.
- Keep user decisions, assistant suggestions, implementation choices, external facts, verification results, and pending questions distinct. Preserve old decisions and append later changes instead of rewriting history.
- Structure tools may report missing, duplicate, unreadable, or broken records. They do not prove source fidelity, memory quality, business completion, or user-path success.
