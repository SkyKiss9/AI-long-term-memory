## Long-running project continuity

- On the first project-related turn in every conversation, use `$maintain-project-continuity` before answering, even if the user only asks whether the skill is installed or whether the assistant knows the project. Read the project's own rules and the complete records named by `.codex/project-continuity.json`.
- A manifest state of `registered`, legacy `installed`, `bootstrapped`, or `handoff-pending` is not activation complete. Continue source inventory, project-local record creation, fresh-task validation, write-back, and commit automatically; do not stop after wiring or merely propose a later bootstrap.
- When the state is `bootstrapped`, this fresh conversation is the cold-start test. Its first project-related answer must fully state the recovered goal, evolution, confirmed decisions and reasons, superseded routes, evidence gaps, current position, unauthorized work, and completion test. A one-sentence status reply or postponing validation fails.
- When the state is `handoff-pending`, this fresh conversation is the required second handoff. Recover the same nine items, explicitly recognize the first task and its natural write-back as complete, and leave only independent evaluation plus final state write-back. Do not restart the first test or ask for a third fresh task.
- The task that performed the first fresh recovery must never promote itself after a follow-up such as “完成” or “交接”. That follow-up is only natural closure and may set `handoff-pending`. Promotion to `cold-start-validated` requires a separate task/conversation with a new task boundary and an independently inspectable source trace; without that evidence, downgrade the result and record the false promotion as a failed test.
- A same-task follow-up is not a fresh conversation. If the current task already performed the `bootstrapped` recovery, its later closure message must stop at `handoff-pending` and cannot satisfy the second-handoff requirement.
- Before sending that answer, explicitly check nine items: goal, evolution, decisions, user reasons, superseded routes, evidence gaps, current state, exact authorization/prohibition boundary, and immediate next action with completion test. An implied or omitted item fails.
- State that this current conversation is performing the test now; do not postpone it to another fresh task. Project facts may come only from manifest-named records. The canonical global skill and this `AGENTS.md` are allowed process instructions, not factual sources. Do not read global memory, old tasks, internet, external project notes, evaluator answers, or non-manifest business documents. Give the actual recorded gaps, not just the label "evidence gaps".
- Acceptance must inspect the fresh task's actual tool/source trace; its own claim of isolation is not proof. Any active read of a forbidden source fails the test.
- The real goal must be the target project's domain goal and user-facing deliverables, not the continuity mechanism itself. State continuity activation separately as the current task; never replace the project purpose with "help the next conversation".
- Invoke it automatically when the user naturally asks to resume or continue project work, for example "继续", "接着上次", or "恢复进度", even if the skill is not named.
- Invoke it automatically before the final response when the user clearly means to finish, close, or hand off the current project conversation, for example "完成", "收尾", "交接", "结束本轮", or "准备开新对话".
- Match intent rather than a literal keyword. Do not treat those words as a closure request when they appear only in a future plan, condition, example, quotation, status description, or unrelated one-off question.
- Keep user decisions, assistant suggestions, implementation choices, external facts, verification results, and pending questions separate. Never guess missing history or silently rewrite an earlier decision.
- At the end of important work or on a genuine closure request, update the project's authoritative timeline and current handoff before replying, then verify the user's real path and repository status. Record partial or blocked work honestly and do not write records when no project state changed. Installing the skill alone is not history reconstruction or acceptance.
