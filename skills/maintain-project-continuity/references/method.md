# Long-Term Project Continuity Method

## Storage and ownership

The continuity workflow is globally reusable, while current project memory is project-local. Each project owns its overview, timeline, current handoff, source index, and acceptance state. Raw Codex conversations and archives remain source evidence and may stay in their original storage. A central method repository may retain frozen pilots and acceptance evidence, but it must not maintain a competing current handoff for another project.

## Registration versus activation

Global discovery and a project trigger only register the workflow. Registration is not a successful activation and must not be reported as ready to use. Activation rebuilds the complete available source boundary into project-local records, makes stale entry points non-authoritative, commits a baseline, passes a genuinely fresh cold-start task that does not name the skill, naturally writes it back, and proves a second fresh task receives the change. A project is directly usable for ordinary continuation only at `cold-start-validated` or `live-validated`.

For a bootstrapped project, the next fresh conversation is the test automatically. Its first project-related answer must demonstrate the recovered context in full; reporting only that records exist or that acceptance remains pending is itself a failed acceptance result.

The globally installed skill and the project's `AGENTS.md` define the procedure and are allowed instruction sources. All factual recovery must still come from the manifest-named project records. Global memory, old tasks, internet material, evaluator answers, external project notes, and project business documents outside the manifest are forbidden during the isolated answer. Review the task's actual tool/source trace before acceptance; the answer cannot certify its own isolation.

After that first result is independently accepted and naturally written back, use `handoff-pending`. This is still not activation complete. The next fresh conversation is the second handoff and must recognize that role from project records; after a complete recovery answer it waits only for independent evaluation and final state write-back. Requiring yet another fresh task repeats the first gate and fails the handoff-position check.

## Three continuous actions

1. Locate every available source: original conversations, complete archives, project files, history, pages, logs, and runtime evidence. Record the source boundary and gaps.
2. Rebuild the story in time order. Each conversation normally gets one to three sentences. A material decision gets its reason, scope, authority, confirmation source, accepted risk, and later status.
3. Hand off the current position. State what is valid, superseded, reopened, unconfirmed, unauthorized, or unfinished, then point to the next authorized action and its completion test.

## Authority order

Use original user conversations for what the user decided. Use project files and commits for what was changed. Use pages, logs, tests, and runtime observations for external facts and verification. Use assistant proposals only as proposals. If two sources disagree, preserve both, identify the conflict, and return to the strongest original source before changing a decision.

## Freshness gate

Before a substantive continuation, compare the source inventory with the available current sources. A new conversation, appended records, changed digest, or changed count makes the old handoff potentially stale. A freshness check can detect that the notes lag; it cannot determine whether a new message is a decision, suggestion, or test result. That identity still needs human-readable timeline maintenance.

## Natural intent gates

- Start gate: a natural request to continue, resume, pick up, or recover a long-running project invokes continuity before substantive work, without requiring the user to name the skill.
- Closure gate: a natural statement that the current project conversation is finished, should be handed off, or should end invokes write-back before the final response.
- Interpret the whole request. Trigger phrases inside plans, conditions, examples, quotations, test data, or unrelated one-off questions do not open the closure gate.
- Closure records the actual state. It never changes partial, blocked, unverified, or unauthorized work into completed work.
- If no material project state changed, closure needs no record rewrite. If the project is only `registered` or legacy `installed`, do not fabricate missing history, but do continue the already-requested activation from all available sources.

## Evidence gates

- Source fidelity: every claimed historical item can be traced to a source location, with duplicates, interruptions, damage, and missing relationships preserved.
- Handoff usability: a task with no old context can answer the project's goal, evolution, decisions and reasons, superseded routes, current state, boundaries, and next completion test from project records alone.
- Real continuation: an authorized fresh task performs a real user-path action, records the result, and writes the state back.
- Independent rerun: a second fresh task receives the updated records and reruns the critical path without relying on the first task's hidden context.

Passing one gate never proves the others. A project may be registered without being bootstrapped, bootstrapped without completing the first fresh test, or `handoff-pending` without passing the second fresh handoff. None of those states proves `cold-start-validated` or `live-validated`.
